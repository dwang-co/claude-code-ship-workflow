# Escalated review hunt — full protocol

Read in full when `/ship` Stage 2's escalation trigger fires (see the trigger paragraph in `SKILL.md`). Relocated out of the always-loaded body per progressive-disclosure guidance — paragraphs below are verbatim from the prior body, in original order. The off-ramp check, the generalize-on-2nd-recurrence rule, and the pattern-propagation check stay in `SKILL.md` because they apply outside a hunt too.

**Escalate to a parallel-adversarial hunt once this branch has produced 2+ real findings across re-review rounds.** The trigger is the *serial* pattern — findings trickling in one at a time across 3+ rounds (fix → re-review → one more thing → fix → re-review → one more thing…) — not simply "the cumulative count of distinct findings across this review arc ever reaches 2." Two reviewers independently converging on real findings in the *same* first round, both fixed in one dispatch, both confirmed clean by both reviewers on re-review, is the process working as intended — that is not itself grounds to escalate. A branch that keeps surfacing one new real issue per round is signaling it's a bug magnet worth heavier treatment, not a queue to keep draining one item at a time. Once the 2-finding threshold is crossed, stop dispatching the standard single code-reviewer+codex pair per fix and instead run a `Workflow`-driven hunt: 3-4 decorrelated reviewer agents, each given the *full* cumulative diff (not just the latest delta) and a different lens (correctness, timing/async-ordering, security/auth, edge-cases/input handling), running in parallel. Apply every real finding from a round in one batch, then re-hunt; converge when 2 consecutive hunts return nothing new — a duplicate of an already-fixed or already-disclosed-and-accepted risk doesn't reset that count, but a genuinely new correctness/security/AC-violating finding always does, no matter how many rounds have already run. This is an orchestration change only — no human checkpoint, no reduction in what gets reviewed — the goal is finding more per round so fewer rounds are needed, not reviewing less. (A genuine architecture/scope question surfaced during any of this — e.g. "this needs a schema change we didn't plan for" — still goes to the user; that's a different kind of stop than "the review loop is running long.") A prompt-reviewer-equivalent agent's findings count toward this threshold the same as `code-reviewer`/`codex review` findings — a real finding is a real finding regardless of which reviewer surfaced it.

**Lens design, not named personas.** When choosing which lenses to run in an escalated hunt, favor
a small number (3-4 — gains peak around here and degrade at 5, per arXiv:2308.07201's own ablation)
of lenses that differ in actual *content* — what each one is told to look for — not
differently-labeled copies of the same instruction; the same paper found a same-role-prompt
multi-agent panel performs identically to a single reviewer, while genuinely diverse roles produced
real gains. Don't add a named persona ("review as an engineering manager," "review like Karpathy")
as a standing lens; if that content is actually wanted, write it as an explicit, content-specific
lens instruction instead (e.g., "evaluate operational ownership, maintenance cost, and whether the
team can safely run this at expected scale" rather than "be an EM"), added to the hunt's lens
rotation the same way the existing four are — conditionally, not run by default on every branch.
Route new lenses through Codex where possible rather than another same-vendor Claude lens —
cross-vendor decorrelation is this pipeline's own best-evidenced lever, and more same-vendor lenses
don't move that axis.

**If an escalated hunt's `Workflow` run comes back with every agent failed or returning `null`** (a connection error, a stall, or similar infra failure across the whole run — not a substantive review), treat that as *the hunt itself failing to execute*, not as a clean result — do not count it toward convergence. Fall back to individual `Agent`-tool dispatches for that round rather than immediately re-invoking the same failed `Workflow` call; a full-hunt infra failure can burn a large amount of budget for zero signal (observed: one such failed run consumed millions of tokens with no usable findings).

**If the off-ramp's structural fix itself starts accumulating real findings across rounds, don't
let "just one more round" become open-ended — pre-commit a stop condition before dispatching the
next round, not after seeing its result.** Apply this whenever a single finding is on its 2nd+ round of fixes after an off-ramp
was already taken once.

**Narrow carve-out: a small, self-contained function (roughly under 20 lines) with a single, well-understood failure mode can stay on single-reviewer targeted re-checks past the 2-finding threshold instead of the full parallel hunt — but only if the orchestrator personally re-verifies each fix with independent test cases before declaring convergence, not just trusting the reviewer's report.** This is a real, evidenced exception: a small JSON-extraction fallback surfaced one new real bug in each of two consecutive re-review rounds — the letter of the threshold rule was crossed — but the orchestrator ran its own reproduction script covering the reported case plus several adjacent edge cases before each round was called done, and it converged cleanly with no further issues found on a broader independent sweep. The parallel-hunt escalation exists to find more per round on a genuine bug magnet; independent verification by a second, different method (the orchestrator's own direct execution, not just another agent's read) can substitute for it when the surface is this small and the failure mode this narrow — it should not substitute for it on anything larger or fuzzier than that.

If an escalated hunt reaches its 3rd round without converging, add one explicit question to that round's synthesis: is there a structural fix — even one out of this diff's scope — that would eliminate the bug category rather than patch the latest instance of it? Record the option, and the user's eventual decision on it, in the round's findings and the PR body even if it isn't built now. **This question re-fires per recurring category, not once per hunt.** As originally written it's asked once, keyed to the hunt's own round count. If a hunt runs long enough to discover a genuinely new bug-magnet category partway through — a different mechanism than whatever triggered the original escalation — that new category gets its own 3-round clock: ask the structural-fix question again when *it* becomes serial, even if an earlier category already received its own structural fix.

**Convergence tracking splits into two buckets — this changes what "2 consecutive hunts return nothing new" actually means, it isn't optional bookkeeping.** Classify every new hunt finding as either:
1. **Release-affecting** — if the artifact is executed or followed as written (code, *or* a runbook/remediation step a human will run against a live system), the finding can change runtime behavior, security posture, deployment/migration success, CI truthfulness, or acceptance-criteria compliance.
2. **Advisory-precision** — correcting it improves explanation, readability, or maintainability, but doesn't plausibly change an operational action or outcome (e.g., a mislabeled cell in a doc describing already-shipped, already-verified behavior).

Convergence requires 2 consecutive hunt rounds with no *new* release-affecting finding. Advisory-precision findings don't reset that counter once explicitly logged or accepted by the user — they're real and worth fixing, but "chase to literally zero via more adversarial rounds" doesn't reliably terminate for prose/documentation the way it does for executable logic. Any disputed or ambiguous classification defaults to release-affecting until the user decides — don't let the split become a way to quietly downgrade a real finding. If 3 consecutive hunt rounds produce *only* advisory-precision findings, stop before dispatching another fix round and ask the user directly: keep chasing precision on this specific artifact, fix what's load-bearing now and log the rest as tracked backlog, or something else.

**When a hunt discovers a new finding category outside the original task's scope** (a real vulnerability or defect unrelated to what the branch originally set out to change — not hypothetical, this has happened), explicitly record with the user whether it's incorporated into the current release scope, fixed only to remove immediate risk with deeper hardening deferred, or moved to tracked follow-up entirely. Incorporating it starts that category's own recurrence counter — it does not just silently fold into and extend the original hunt's counters indefinitely.

**A fix only counts as "structural" (per the re-firing question above) if it does at least one of:** makes the invalid state unrepresentable or unreachable (architecture, types, a privilege/permission boundary); derives or generates the artifact from its authoritative source, so it can't drift independently of what it describes; checks the property behaviorally or exhaustively via a real, executable test; or replaces an open-ended representation with a bounded one whose own completeness/consistency is itself validated. **Reorganizing human-authored content into a clearer format does not qualify by itself** — a markdown table isn't more "structural" than the prose it replaced unless something also automatically checks the table's claims against the actual code; it can go stale exactly the way a paragraph can, just cell-by-cell instead of sentence-by-sentence. Label a reorganization-only change a readability/auditability improvement, and keep that category's recurrence counter active rather than treating it as resolved. A check that verifies partial correctness — presence or position, but not completeness or exclusivity — doesn't fully qualify either, even though it looks structural: "the expected content exists somewhere in this range" is a real improvement over no test, but it isn't "only the expected content exists."

**Before re-dispatching a hunt round after applying a round's fixes, verify each fix against the exact gap it claims to close — don't just trust the fix description and move straight to the next full hunt.** Reproduce the specific bypass/scenario a logic fix targeted, confirm it's actually closed, and sweep at least one adjacent/sibling case the same class of bug could also occur in (this is the same discipline the pattern-propagation check above already requires — apply it to the round's own fixes, not just to sibling call sites). For a doc/runbook fix, re-check the specific claim against the actual code or scenario it describes, not just against the reviewer's suggested wording. Then get a second opinion before redispatching: call `advisor()` with the fix and the exact gap it claims to close, stated explicitly, and weigh its read seriously per this harness's own advisor-tool guidance. **If advisor is unavailable** (an explicit error, not just a normal response you disagree with), fall back to `/dual-review`: write a short, self-contained brief naming the specific fix and the specific gap it's meant to close, dispatch Claude + Codex in parallel and blind, and instruct both to (1) validate the fix actually closes the gap, (2) do a short root-cause pass on why the prior instance was wrong, and (3) propose a recommendation path forward — only then move to the next full hunt round. This is cheap relative to a full hunt round, and skipping any independent check here has proven expensive: a round-10 fix was never actually wired into the workflow it was supposed to be called from, caught only by round 11's fresh hunt rather than by a pre-redispatch check; a round-13 documentation matrix had new, independently-findable errors in it the moment it was introduced, which a second read against the actual source it describes would very likely have caught before the next hunt round did.

**Flagged experiment, not a standing rule — sentinel-mode lens rotation.** Once a specific finding *category* (not "the highest-risk category" in the abstract, and not a specific lens) has gone quiet for its own 2-3 consecutive rounds under the two-bucket counting above, that category can move to a lighter-touch "sentinel" pass rather than full-depth scrutiny every round: subsequent rounds give full attention to still-active categories, while one rotating lens does a lighter regression check of the quieted category. Reactivate full coverage on that category immediately if: code or guidance touching it changes, a new finding elsewhere depends on one of its assumptions, the sentinel pass finds something substantive, or the hunt is about to declare convergence (always run one final full-depth pass across every category before declaring done, regardless of sentinel status). **Do not de-escalate a whole lens just because one category it's associated with converged** — evidence argues against that specific shortcut: a lens's associated "highest-risk" category can go clean while the same lens keeps finding real issues in a *different* category (e.g. documentation precision) for many more rounds. Category-based sentinel status, not lens-based dropping. If tried, track token/time cost and findings-caught-by-sentinel-vs-full-pass for a few hunts before deciding whether to promote this to a standing rule.

Escalating to the multi-lens hunt doesn't drop cross-vendor review: run `codex review --base main` (via the project's wrapper if it provides one) alongside the first escalated hunt round, and again before declaring convergence, at minimum. `Workflow`'s `agent()` calls are Claude-only, so a hunt that never re-invokes Codex silently reintroduces the same-vendor-only risk this stage already treats as load-bearing for the non-escalated path.
